# 커뮤니티 대화 연결 개선 검토 기록

작성일: 2026-09-27. **실제 앱 소스와 SQL 수정안을 준비한 상태이며, 승인 전 운영 DB 적용·main 배포는 하지 않았다.** 아래 검증 결과는 로컬·격리 환경의 결과다. 실제 운영 회원 두 명이 글과 답글을 작성하는 검증은 아직 하지 않았다.

이번 목적은 회원이 다른 사람의 이야기를 읽고, 공감하고, 댓글·답글로 대화한 뒤 돌아올 수 있도록 끊긴 연결을 고치는 것이다. 판매·수수료·포인트 정책 개편, 매장·라이브 연계, 모집·광고 집행은 이번 범위에 포함하지 않는다. 기존 테스트 글은 기능 확인용으로 취급한다.

## 1. 앱에서 달라지는 동작

| 영역 | 준비한 변경 |
|---|---|
| 홈·하단 이동 | 홈에서 회원 이야기를 먼저 접하도록 순서를 조정하고, 하단에 소식 진입점을 둔다. 홈의 이야기에서 해당 원글로 이동한다. |
| 읽기·누르기 | 이야기 본문 16px, 댓글·소식 본문 15px, 댓글 입력 16px로 조정한다. 댓글의 주요 동작 버튼 높이는 44px 이상으로 확보한다. |
| 댓글·답글 | 일기·게시판·질문 답변의 댓글 처리를 공통화한다. 댓글 조회 실패를 “댓글 없음”으로 표시하지 않고 재시도할 수 있게 한다. 댓글 50개 이후에도 더 볼 수 있고, 소식에서 지정한 댓글까지 찾아 이동한다. 일기에는 부모 댓글에 답글을 단다. |
| 작성 중 내용 | 계정·원글·부모 댓글을 구분해 같은 탭의 초안을 임시 저장한다. 로그인·프로필 방문 후 돌아오는 경로와 댓글 위치를 보존하고, 등록 실패 때 작성 내용을 유지한다. 삭제는 실제 삭제된 행을 확인해 성공 여부를 표시한다. |
| 소식 | A의 글에 B가 댓글을 달고 A가 답하면 B에게 답글 소식이 생기도록 한다. 댓글 ID로 해당 대화에 연결하며, 친구 신청·수락 소식도 연결한다. 읽음 처리는 조회한 소식 시점을 기준으로 하여 이후 도착한 소식을 함께 읽음 처리하지 않는다. |
| 프로필·친구 | 신청 전·신청 보냄·신청 받음·친구 상태와 수락·거절·취소·해제 동작을 맞춘다. 조회 오류를 “친구가 아님”으로 단정하지 않고 재시도 경로를 제공한다. |
| 숨김·익명·과거 글 | 이번 RPC 조회 경로에서 숨김 원글과 숨김 부모 댓글을 댓글·소식 조회에서 제외한다. 익명 게시판·질문 답변의 소식은 작성자 프로필 링크를 드러내지 않는다. 최신 목록 밖의 오래된 일기와 과거 공개 질문 답변도 ID로 찾아 연결한다. |

임시 저장은 서버 동기화가 아닌 `sessionStorage` 기반이다. 다른 기기나 새 탭까지 이어지는 초안 보존으로 해석하면 안 된다.

## 2. 승인받을 SQL 범위

첫 번째 파일은 [community_conversation_integration.sql](../supabase/community_conversation_integration.sql)이다.

| 구분 | 함수 | 목적 |
|---|---|---|
| 신규 | `get_community_diary`, `get_community_answer` | 원글·과거 답변을 정확한 ID로 조회 |
| 신규 | `get_diary_comment_thread` | 공개된 일기의 댓글·답글 및 허용된 프로필 연결 정보 조회 |
| 신규 | `get_community_news`, `mark_community_news_seen` | 답글·친구 소식, 댓글 ID, 시점 기준 읽음 처리 |
| 수정 | `get_diary_comments`, `get_board_comments`, `get_answer_comments` | 원글·부모 댓글의 공개 상태 확인 |
| 수정 | `get_my_news` | 기존 반환 필드를 유지하면서 새 소식 조회와 연결 |

두 번째 파일은 [community_friend_request_lock.sql](../supabase/community_friend_request_lock.sql)이다. 기존 `request_friend`, `respond_friend`, `remove_friend`가 같은 두 회원에 대해 같은 트랜잭션 잠금을 사용하도록 수정한다. 반대 방향의 동시 신청을 처리하기 위한 변경이며, 기존 함수 인수·반환 형식과 로그인 전용 실행 권한은 유지한다.

두 SQL은 함수 정의와 실행 권한을 적용한다. **기존 게시물·댓글·친구 행을 일괄 수정하거나 삭제하지 않으며, 포인트 적립액·한도·구매 규칙도 변경하지 않는다.** 댓글 생성·포인트 지급 함수와 공용 `is_admin()`·`claim_mission`은 교체하지 않는다. 과거에 이미 생긴 역방향 친구 중복 행도 자동 정리하지 않는다. 존재 여부를 먼저 읽기 조회하고 필요하면 별도 보정안을 검토한다.

## 3. 확인한 결과와 검증 한계

| 검증 | 현재 기록 | 의미와 범위 |
|---|---|---|
| 실제 SQL 격리 실행 | **9/9 통과** | 기존 답글 소식 누락 재현 후 수정 확인. 댓글 ID·수신자 중복·숨김·과거 글·익명 링크·읽음 시점·RPC 권한·친구 처리 검증. |
| 댓글 API 계약 | **10/10 통과** | 댓글 조회·생성·삭제의 인수, 실패 구분, 삭제 행 확인 등 서비스 계약 검증. |
| 친구 상태 검증 | **31개 assertion 통과** | 신청·응답·조회 등 친구 처리의 기대값 검사. 31개의 독립 사용자 시나리오를 뜻하지 않는다. |
| 최종 두 브라우저 격리 검증 | **16/16 통과** | 최신 main 기반 프로덕션 빌드에서 두 별도 Chromium 프로세스와 격리 SQL을 연결. 댓글·답글·친구·뒤로 복귀·초안·실패 후 재시도·50개 이후 댓글·읽음 이후 새 소식·320/390/480/1440px 소식 화면을 확인. JavaScript 오류와 예상 밖 fixture 요청 실패 0건. |
| 최신 main 기반 빌드 | **통과** | `c73797b` 독립 작업트리에 이번 대상 22개 파일만 적용한 정식 빌드 통과. |
| 운영 읽기 전용 사전 확인 | **역방향 친구 중복 0건** | 댓글 테이블 3개의 기존 RLS도 확인했다. 운영 함수·정책·데이터 변경은 하지 않았다. |

독립 검토에서 나온 세 항목도 수정하고 최종 브라우저 검증에 포함했다. 브라우저 뒤로가기에서 대화 위치를 복원하고, 프로필 조회 실패를 정상적인 빈 결과와 구분하며, 소식 읽음 처리 후 서버 재조회로 완료 순서와 시각 판정을 맞췄다.

SQL 검증은 [재현 안내](../scripts/community-tests/README.md)와 [실행 스크립트](../scripts/community-tests/test-community-sql.mjs)에 남겼다. 저장소 밖의 PGlite 런타임으로 실행하며, 실제 함수 원문과 두 변경 SQL을 메모리 DB에 적용한다.

검증에는 다음 한계가 있다. 운영 Supabase Auth·전체 RLS 정책·Storage, 알림 푸시, 실기기 앱 동작은 확인하지 않았다. `auth.uid()`는 가상 계정 claim으로 구현했고 `claim_mission`은 항상 0점을 반환하는 대체 함수이므로 실제 포인트 지급 검증이 아니다. 단일 PGlite 연결에서 친구 흐름을 순차 실행했으므로 **실제 두 DB 세션의 동시 요청·잠금 경합도 아직 검증하지 않았다.**

운영에서 읽기 확인한 댓글 테이블 3개에는 본인 정책 `own_all`, 관리자 정책 `admin_all`, 댓글 자체의 `status='visible'`만 확인하는 `public_read`가 있다. **테이블 직접 REST 조회의 기존 RLS는 부모 원글의 공개 상태를 확인하지 않는다. 이번 SQL은 RLS를 바꾸지 않으므로 부모 원글과 RLS의 공개 상태 동기화는 미포함이다.** 따라서 이번 RPC 수정이 전체 접근 경로의 숨김·익명성을 해결했다고 볼 수 없다. 이 부분은 별도 「앱 전체 기능 점검」의 기존 권한·정책 점검 범위로 남긴다.

## 4. 반영 범위와 승인 후 순서

현재 기능 브랜치와 main에는 서로 포함되지 않은 커밋이 50개/21개 있어 전체 브랜치를 병합하면 다른 작업이 함께 들어갈 수 있다. **전체 병합은 하지 않는다.** 최신 `origin/main`의 `c73797b`에서 만든 독립 작업트리에 이번 대상 22개 파일만 선별 적용하여 정식 빌드가 통과했다. 최종 반영 파일 목록·커밋은 책임 작업자가 확정한다.

운영 반영 승인을 받은 뒤 다음 순서로 진행한다.

1. 교체 대상 운영 함수의 기존 정의·실행 권한을 백업하고, 신규 함수 목록을 구분해 복구 기준을 남긴다.
2. 적용 직전 역방향 친구 중복 행 수를 `SELECT`로 재확인한다. 현재 사전 확인은 0건이다. 이후 중복이 생겨도 이번 SQL이 자동 보정하는 것으로 취급하지 않는다.
3. 승인된 두 SQL을 적용한다. 실패하면 적용 상태부터 확인하고 임의로 데이터 보정을 추가하지 않는다.
4. 운영에서 함수 존재·권한·반환 형식·공개 상태 필터를 읽기 조회로 확인한다. 실제 회원 글·댓글 작성 검증은 별도 실행 범위를 명확히 한 뒤 진행한다.
5. 최종 확장 회귀 검증과 최신 main 빌드가 통과한 **이번 변경 커밋만** main에 반영한다.
6. Vercel 배포 완료와 실제 서비스에 해당 버전이 반영됐는지 확인하고 결과를 기록한다.

이 기록은 변경 검토와 승인 판단을 위한 자료다. 로컬 테스트 통과를 운영 배포 완료나 실제 회원 대화 검증 완료로 대신하지 않는다.
